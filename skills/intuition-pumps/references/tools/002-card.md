# 002 归谬

## 身份

- 原书标题（中文）：归谬法：发现错误命题的妙招

- 原书分组：第一部分 通用思考工具
- 中文短命令：/归谬
- 别名：02、工具02、归谬法、归谬法：把命题推到它承受不了的地方
- 工具家族：论证检验
- 默认输出重量：中等。输出强版本命题、辅助前提、推论链和需要放弃的环节。
- 对应 issue：ISSUE-011 / TOOL-002

## 名称与思想实验

“归谬法”这个名字来自一种古老的反证手法：先临时接受某个命题或假设，再把它按自身逻辑推下去；如果最后得到矛盾、荒唐后果或无法接受的代价，就说明原命题、辅助前提或推理链里至少有一处需要放弃。丹尼特把它称为理性研究的撬棍和一致性的杠杆，因为它不是从外部强行否定，而是让命题自己承受自己的后果。

原书标题里的英文还有一个玩笑：`parity of reasoning` 被误拼成 `parody of reasoning`，于是出现了“以蠢类推”的影子。这个玩笑很关键，因为它提醒我们：坏的归谬常常只是把对方观点演成可笑版本，再顺手嘲笑。那不是推理，而是 parody。真正的归谬必须让对方承认起点和推论步骤，否则只是稻草人。

丹尼特给出的几个例子都在练这个分寸：如果有人说心灵就在某种分子里，可以问把这种分子倒掉是否等于杀人；如果有人把红色意识简化为红敏神经元的活动，可以问培养皿里被刺激的神经元是谁在体验红色；如果有人把意识放进微管量子效应，可以问断手上的微管是否也该接受麻醉。它们的共同动作是：不先宣布对方错，而是把对方的归属关系推到一个更清楚、更难承受的位置。

## 原书机制转译

归谬法解决的是一种常见卡点：你觉得某个主张不对，但直接反驳时说不清问题在哪。它的做法不是立刻否定，而是暂时把对方命题当真，并尽量使用对方能接受的强版本。然后沿着命题和必要辅助前提推出后果。

如果推到某一步出现矛盾、事实不可能、概念自毁，或价值上明显不可接受，就说明问题不一定在原命题本身，也可能在某个辅助前提或推理步骤。好的归谬必须指出“哪里承受不住”，而不是只展示一个好笑结论。

## 用户模式

### 触发场景

- 某个观点看起来可疑，但你暂时说不清问题在哪里。
- 对方主张依赖很强的前提，例如“所有、必须、只要、绝不、一定”。
- 你需要检验一个原则能否推广到相邻案例或极端案例。
- 你想批评一个命题，但不想把它变成稻草人。

### 操作步骤

1. 用最强版本重写被检验命题，让支持者也愿意点头。
2. 写出推理需要的辅助前提。不要把这些前提偷偷塞进结论里。
3. 从命题推出第一层后果，再推出第二层后果。
4. 标出冲突发生的位置：事实冲突、概念冲突、价值冲突，还是实践后果不可接受。
5. 判断该放弃什么：原命题、辅助前提、适用范围，还是某个推理步骤。
6. 给出降级版命题，而不是只说“所以它荒谬”。

### 输出结构

```text
强版本命题：
辅助前提：
推论链：
假设 X 为真 -> 则 Y -> 则 Z -> 但 Z 与 A 冲突。
冲突类型：
建议放弃或降级：
```

## agent 自救模式

### 卡住信号

- 我只是在说“这个主张有问题”，但没有指出问题位置。
- 我准备反驳，却没有先写出对方能认可的强版本。
- 当前命题里有“所有、必须、绝不、只要”等强量词。
- 我需要测试一个规则推广后是否会自毁。

### 自救动作

1. 暂停直接反驳，先写强版本命题。
2. 显式列出辅助前提。
3. 推出两步后果，不跳步。
4. 标注冲突类型。
5. 输出一个降级版或限定版命题。

### 轻量输出

```text
工具：/归谬
当前卡点：我觉得命题有问题，但没有定位问题。
本工具给出的改写或检查：先接受强版本，再推出后果并标出冲突。
下一步：决定要放弃原命题、辅助前提还是适用范围。
```

## 误用边界

- 不要把归谬变成稻草人。对方不承认的辅助前提，不能算作对方命题的后果。
- 不要把“我觉得极端”当成归谬。必须说明冲突发生在哪里。
- 不要用荒诞例子替代推理链。荒诞只是信号，不是证明。
- 归谬适合检验原则和强命题，不适合替代事实调查。

## 小测试问题

请用 `/归谬` 检验这个命题：“一个 agent skill 越自动化越好，最好所有工具卡都自动生成。”

## 测试运行结果

强版本命题：

如果目标是效率，那么 agent skill 的工具卡越自动化越好；理想情况下，所有工具卡都应自动生成，以节省人工时间。

辅助前提：

1. 工具卡之间差异不大，可以共享同一种生成流程。
2. 自动生成的卡片能保留每个工具的关键机制和误用边界。
3. 节省生成时间比逐卡判断更重要。

推论链：

假设“所有工具卡都应自动生成”为真 -> 那么每张卡可以主要通过同一模板和同一流程产出 -> 那么工具之间的机制差异会被压平，测试也容易变成格式检查 -> 但这与“每个工具必须单独判断如何从文本变成 skill 命令工具”的目标冲突。

冲突类型：

实践目标冲突。该命题追求效率，但破坏了本项目最重要的质量约束。

建议放弃或降级：

放弃“所有工具卡都自动生成”。可降级为：基础设施、索引和验证检查可以机械化辅助；每张工具卡的机制转译、小测试和验收必须逐卡完成。

测试结论：通过。本工具没有直接嘲笑原命题，而是先给出强版本，再列辅助前提，推出与项目目标冲突的后果，并给出降级版命题。
