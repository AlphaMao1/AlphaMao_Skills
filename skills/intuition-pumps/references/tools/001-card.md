# 001 犯错

## 身份

- 原书标题（中文）：犯错儿：犯“好”错儿才有价值
- 英文原名：Making Mistakes
- 中文标题来源：书内译名 + 自拟功能副题。短命令“犯错”和卡片标题“用好错误换取可修正的理解”是 skill 化后的操作性改写。
- 原书分组：第一部分 通用思考工具
- 中文短命令：/犯错
- 别名：01、工具01、犯错儿、犯错儿：用好错误换取可修正的理解
- 工具家族：论证检验
- 默认输出重量：中等。输出一个可被打脸的版本、脆弱前提清单和修正记录。
- 对应 issue：ISSUE-010 / TOOL-001

## 名称与思想实验

丹尼特这一节的名字很朴素：犯错。它背后的画面不是莽撞、粗心或降低标准，而是把“错误”当成可以被观察、定位和修正的中间产物。原书先把哲学史描述成一串聪明人犯下的诱人错误：学这些错误，不是为了崇拜失败，而是为了知道哪些坑会反复吸引聪明人。

书里接着用了几个具体场景来压实这个工具。学生因为怕写错而卡在开头，丹尼特催他们先写出东西；做长除法时，孩子以为数学不该靠猜，后来才明白先猜一个数、算出偏差、再修正，正是方法的一部分；航海定位也是先假设一个精确位置，再用太阳实际位置校正；魔术师则把一连串失败藏在表演流程里，只让成功的猜测留下“奇迹”效果。

所以“犯错”这个名字对应的操作不是“随便错”，而是“犯一个足够清楚的错”。只有错误清楚，后续证据才知道该打在哪里；只有错误可恢复，试错才不会变成冒险；只有错误被记录，下一轮理解才会真的长出来。

## 原书机制转译

这个工具解决的不是“怎样避免错误”，而是“怎样把不可避免的早期错误变成认知资产”。在探索、写作、设计和概念建模中，最危险的状态常常不是错，而是为了避免错而停留在含糊、安全、无法检查的表达里。

“犯错”的机制是：先把当前理解压成一个具体版本，让它足够明确，能够被证据、他人反馈或后续推理击中。一个好错误至少满足三点：

- 具体：别人知道你到底主张了什么。
- 可定位：错了以后能找到是哪一个前提、变量或范围错了。
- 可恢复：修正成本可承受，不会造成不可逆损害。

这个工具把“我还没想清楚”改造成“我先写一个可修正版本，然后主动暴露它最可能错的地方”。

## 用户模式

### 触发场景

- 你卡在开头，不敢下判断。
- 你害怕写错，导致一直只写抽象话。
- 讨论停在“这个问题很复杂”，但没有可检查版本。
- 你正在做探索性方案、文章大纲、概念设计、研究假设或产品判断。
- 当前任务允许低成本试错，且错误可以被发现和修正。

### 操作步骤

1. 写出一个“当前最可信但可能错”的版本。不要写成中庸废话，要让它能被反驳。
2. 标出 2-3 个最脆弱前提：事实前提、因果前提、用户假设、概念边界或价值判断。
3. 为每个前提写一个可能打脸它的证据或反馈。
4. 主动寻找纠错来源：日志、测试、读者、专家、用户反馈、反例或更强对手观点。
5. 把发现的错误改写成修正记录：`我以为 X，因为 Y；现在发现 Y 忽略了 Z；所以下一版改成 W。`
6. 保留这条修正记录，防止下一轮重复同一种错。

### 输出结构

```text
可被打脸版结论：

最脆弱前提：
1.
2.
3.

可能打脸证据：
1.
2.
3.

修正记录：
我以为……因为……；现在发现……；所以下一版……
```

## agent 自救模式

### 卡住信号

- 我迟迟不给出可检查判断，只反复说“需要更多上下文”。
- 我在用安全、抽象、不会错的话替代推进。
- 我无法确定完整方案，但可以给出一个低风险草稿。
- 当前任务处于探索阶段，不是不可逆执行阶段。

### 自救动作

1. 明确告诉自己：先产出一个可被打脸的版本，而不是等到全知。
2. 把当前判断写成一句可反驳结论。
3. 标出最可能错的 2-3 个点。
4. 给出下一步最小验证动作。
5. 如果任务是高风险执行，停止使用本工具，转入风险控制。

### 轻量输出

```text
工具：/犯错
当前卡点：我还没有足够把握，但继续含糊会阻止推进。
本工具给出的改写或检查：先给出一个可被打脸版本，并列出最脆弱前提。
下一步：用一个最小证据或反馈验证最脆弱前提。
```

## 误用边界

- 不适用于不可恢复或高代价错误：外科、飞行、删库、发布、凭据处理、生产安全、法律承诺等。
- 不等于“粗心也没关系”。好错误必须具体、可定位、可恢复。
- 不适合用来逃避基本功。如果已有明确规范、测试或事实来源，应先查证，而不是故意猜。
- 不要把“我愿意犯错”包装成免于负责。犯错后的修正记录是本工具的一部分。

## 小测试问题

我想设计一个新的 agent skill，但一直怕方向错，所以迟迟不敢写第一版。请用 `/犯错` 产出一个可被打脸版结论，并列出最可能错的 3 个前提。

## 测试运行结果

可被打脸版结论：

这个 skill 的第一版应该先服务一个窄场景：用户遇到难题时，让 agent 推荐 5 个思考工具，并先应用一个最合适的工具。

最脆弱前提：

1. 用户真的愿意先看 5 个候选，而不是希望 agent 直接给答案。
2. 5 个候选足以避免路由塌缩，但不会让选择负担过高。
3. 思考工具能被稳定转成可执行步骤，而不是变成哲学术语解释。

可能打脸证据：

1. 用户反复跳过候选菜单，只要求直接处理。
2. 路由记录显示 5 个候选仍然集中在少数高频工具。
3. 小测试发现某些工具只能解释概念，不能产出下一步动作。

修正记录示例：

我以为“先推荐 5 个工具”是最好的默认入口，因为它能覆盖多样性；现在发现用户在推进场景可能不想选择；所以下一版区分“菜单模式”和“推进模式”。

测试结论：通过。本工具把“害怕方向错”转成了一个可检查版本、三个脆弱前提和可观察的打脸证据，符合“好错误暴露隐藏假设”的机制。
